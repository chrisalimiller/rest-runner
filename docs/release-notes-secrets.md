# Release notes draft: secrets in the system keychain

Release notes are generated by GitHub (`releases/generate-notes` in `.github/workflows/build.yml`) and there is no changelog file, so this is a draft to paste into the release body after the generated notes (it also shows in the update dialog).

## Secret variables now live in your system keychain

- Values of environment variables marked **secret** are now stored in the macOS Keychain or Windows Credential Manager instead of the app's local storage. The variable's name and secret flag stay where they were, with an empty value.
- On first launch the app moves existing secret values for you. Nothing is removed from local storage until the keychain has confirmed the value. If the move cannot finish, it is retried at the next launch.
- macOS may ask for Keychain access on first launch. Choose Allow (or Always Allow).
- If the keychain is locked or access is denied, secrets work for the current session only and a banner offers Retry. They are never written back as plain text.
- Known secret values are now masked in history, saved runs and script variables. Script variables with credential-like names are not saved.
- Workspace export still leaves secrets out by default; importing a file with blank secrets keeps the values you have.
- Credentials typed straight into a header or auth field are not protected and now show a **Plain text** badge. Use a secret variable instead.

**Downgrading:** older versions read secrets from local storage only, so after this update they will see empty values for secret variables. Export your workspace with secrets included first if you may go back.

See [Secret variables and the system keychain](data-and-storage.md#secret-variables-and-the-system-keychain).
